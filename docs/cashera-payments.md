# Переход на Cashera

Новые покупки поддерживают Cashera: Plus, поддержку проекта, VPN, комплект VPN + Plus,
промокоды и боевой пропуск. Существующие заказы и callback Platega сохраняются.
Изменения схемы БД не требуются.

## Настройка магазина

В `.env.production` на каждом узле приложения задать:

```dotenv
PAYMENTS_ENABLED=true
PAYMENTS_PROVIDER=cashera
CASHERA_API_KEY=<ключ магазина pk_...>
CASHERA_API_SECRET=<секрет магазина sk_...>
SITE_URL=https://animonster.su
```

Секреты не хранить в Git и не отправлять в клиентский код.
`PLATEGA_MERCHANT_ID` и `PLATEGA_SECRET_KEY` оставить для старых заказов.
Без `PAYMENTS_PROVIDER` используется Platega: это позволяет подготовить код до переключения магазина.
При явно выбранной, но ненастроенной Cashera новые покупки блокируются, скрытого переключения на Platega нет.

В кабинете Cashera включить уведомления и указать:

- Callback: `https://animonster.su/api/payments/cashera/webhook`
- Success: `https://animonster.su/pins?payment=return`
- Fail: `https://animonster.su/pins?payment=failed`

Создание заказа передаёт собственные success/fail URL для соответствующего товара.
Способ оплаты не передаётся: покупатель выбирает доступный способ на общей форме Cashera.
Если включён список разрешённых IP магазина, добавить исходящие IP всех серверов приложения.

## Проверка и включение

1. Развернуть код, сохранив `PAYMENTS_PROVIDER=platega` до готовности магазина.
2. Применить Caddyfile с удалением `X-Secret`, `X-Api-Key`, `X-Merchantid` из access-логов.
   Проверить конфигурацию перед перезапуском. При bind mount после замены файла через Git
   пересоздать контейнер Caddy, чтобы он читал новый файл.
3. Подключить ключи через защищённый доступ к серверу, переключить provider и пересоздать
   контейнеры приложения на всех узлах (обычный restart не обновляет env_file).
4. В кабинете Cashera отправить тест вебхука: ожидается HTTP 200, без выдачи покупок.
5. Проверить создание ссылки и возвращение на нужный товар. Реальную контрольную оплату
   выполняет владелец магазина; после неё проверить однократную выдачу и статус заказа.

Автоматические проверки используют подменённый API и локальную PostgreSQL-совместимую БД;
они не создают реальные платежи. Реальный магазин и получение уведомлений нужно проверить после подключения ключей.

## Гарантии обработки

- В Cashera сумма передаётся целым числом копеек; сверяется исходный `amount`, а не `net_amount`.
- `external_id` — неизменяемый ID заказа AniMonster. При потере ответа проверяется тот же заказ
  через поиск по external_id. При полной недоступности провайдера заказ сохраняется для сверки.
- Callback проверяет оба заголовка в постоянном времени, затем запрашивает актуальное состояние
  из API. Переход на success URL сам по себе не выдаёт покупку.
- Только `paid` подтверждает оплату; `canceled`, `failed`, `expired` отменяют ожидание.
  Позднее подтверждение допускается. `refunded` и `chargeback` используют существующий внутренний
  статус `chargebacked` и механизм отзыва доступа; постоянная косметика следует прежним правилам проекта.
- Повторная доставка не создаёт второй grant. Возвращённый платёж не активируется повторно.
- Кнопка проверки выбирает провайдера сохранённого заказа. Cashera без сохранённого UUID
  сверяется по external_id. Администратор пропуска может указать ID заказа или транзакции.
- Отключение новых продаж не мешает проверке старых платежей.
- Для отката новых покупок переключить `PAYMENTS_PROVIDER=platega`, сохранив оба комплекта ключей:
  поступающие уведомления Cashera должны продолжать обрабатываться.
