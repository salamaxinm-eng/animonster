## Архитектура

- Next.js 16.3.6 App Router, React 19.2.6, TypeScript; backend — Route Handlers и `lib/server`, PostgreSQL через `postgres`. Для разработки существует PGlite.
- Публичные страницы используют смешанный рендеринг: серверные страницы передают данные React-компонентам с `use client`. Само наличие `use client` не означает отсутствие HTML: карточки с серверными начальными данными уже рендерились на сервере.
- Карточки `/anime/[id]` принимают числовые ID, ID со slug и алиасы; canonical ведёт на числовой ID. Плеер, история, озвучки и комментарии загружаются отдельно в браузере.
- `anime_cache` содержит реальные данные провайдеров; жанры/темы классифицируются через существующую таксономию; связи франшиз хранятся отдельно.
- Главная использует `cachedHomePopular`; каталог — `cachedCatalogPage`; sitemap и robots создаются Metadata Routes. Нового фреймворка или отдельной версии сайта для роботов нет.

## 🔴 Критические проблемы обнаружения контента

### 1. Жанровые страницы зависели от JS

**Где:** `app/genres/[genre]/page.tsx`, `components/genre-catalog.tsx`. Сервер отдавал H1, а клиент начинал с пустого массива и загрузки API. Подтверждение: у «Комедии» в HTTP-HTML нет карточек и внутренних ссылок.

**Влияние:** обход жанров не давал роботу немедленного доступа к списку тайтлов; страница имела общие метаданные.

**Исправлено:** серверная выборка существующего каталога с limit/offset; уникальные Title, description, H1 и canonical; `CollectionPage`/`ItemList`; обычные ссылки пагинации. Восстановлено декодирование кириллических параметров, требуемое установленным runtime. Неизвестный жанр и страница за пределами списка вызывают `notFound`. Темы по-прежнему перенаправляются в существующий поиск.

**Файлы:** два указанных выше, `components/catalog-pagination.tsx`, `components/seo-json-ld.tsx`, `lib/seo.ts`.

**Проверка:** запросить `/genres/%D0%9A%D0%BE%D0%BC%D0%B5%D0%B4%D0%B8%D1%8F` без JS; найти названия, `<a href="/anime/...">`, метатеги и JSON-LD. В локальной выборке — 12 тайтлов и 24 ссылки. Проверить неизвестный жанр: 404.

### 2. Пагинация не создавала доступные роботу страницы

**Где:** `app/catalog/page.tsx`, `app/catalog/client-page.tsx`, прежний `components/genre-catalog.tsx`. Состояние страницы было только в React, кнопки не имели href. Сервер каталога игнорировал `page`.

**Влияние:** HTTP-запрос второй страницы повторял первую, canonical также ссылался на первую; робот не получал последовательный путь по каталогу.

**Исправлено:** сервер читает page/tab/sort, получает нужный offset; Title, description и H1 учитывают страницу; canonical сохраняет page и онгоинги. Пагинация использует href с prev/next. Сортировка сохраняется в URL; вариант `sort=fresh` имеет noindex, follow и canonical основной сортировки соответствующей страницы. Неизвестные параметры не входят в canonical. Переходы больше не запускают немедленную повторную загрузку каталога клиентским API.

**Файлы:** оба файла каталога, `components/catalog-pagination.tsx`, `lib/seo.ts`.

**Проверка:** сравнить наборы ID на `/catalog` и `/catalog?page=2`; canonical второй страницы должен содержать page=2. Локально списки различаются, в JSON-LD вторая страница начинается с позиции 25. В браузере работает переход 2 → 3, на последней странице отсутствует активная ссылка «Далее».

## 🟠 Высокий приоритет

### 3. Несуществующие тайтлы и жанры отвечали 200

**Где:** `app/anime/[id]/page.tsx`, `app/genres/[genre]/page.tsx`. На production проверены `/anime/999999999`, `/anime/invalid_seo_id`, `/genres/unknown-seo-genre`.

**Влияние:** soft 404 и трата обхода. Noindex заглушки аниме уже присутствовал, но HTTP-статус был неверным.

**Исправлено:** серверный `notFound`; добавлен компонент 404 с H1 и ссылкой в каталог. В тестовом runtime код ответа 404 и noindex подтверждены, но в исходном HTML ответа содержимое компонента отсутствует, а браузер не смог отобразить его из-за описанной выше проблемы JS. Пользовательский вид 404 требует проверки staging. Страница аниме сначала читает имеющуюся карточку из локального кэша, не ожидая повторного поиска видео у провайдера. Сбой источника/БД не превращается в «тайтл не существует»: обычные ошибки пробрасываются, только подтверждённое отсутствие/404 даёт notFound. У lookup алиасов добавлен строгий режим для серверной страницы; существующие вызовы API сохраняют прежний интерфейс.

**Файлы:** `app/not-found.tsx`, две страницы, `lib/server/anime.ts`, `lib/server/library.ts`.

**Проверка:** HTTP 404 для неизвестных URL; известный тайтл при наличии кэша продолжает иметь основной HTML при недоступном источнике. Регрессии отдельно проверяют отличие временного сбоя от отсутствия.

### 4. Robots закрывал изображения

**Где:** `app/robots.ts`: запрет `/api/` распространялся на `/api/image`, используемый в `posterUrl`.

**Влияние:** робот не мог свободно загружать постеры по указанным в страницах адресам. Это не доказывает причину конкретных позиций в Яндексе.

**Исправлено:** снят общий запрет API, сохранены/уточнены ограничения административных, личных, VPN, офлайн- и авторизационных маршрутов. CSS и JS доступны. Авторизация API остаётся обязанностью backend, robots не является защитой данных.

**Файл:** `app/robots.ts`.

**Проверка:** получить robots.txt, убедиться в отсутствии общего Disallow /api/; проверить конкретный URL постера в инструменте анализа robots Яндекс Вебмастера. В будущем можно ограничить отдельные служебные API по фактическим логам обхода.

### 5. Главная и рекомендации не давали HTML-ссылок на тайтлы

**Где:** `components/popular-hero.tsx`, `app/recommendations/page.tsx`.

**Исправлено:** просмотр в слайде стал обычной ссылкой с сохранением имеющегося обработчика открытия для обычного клика. Модификаторы клика позволяют стандартную навигацию. Гостевая подборка рекомендаций строится сервером существующим `fallbackRecommendations`; затем клиент сохраняет возможность персонализировать список. Для подборки добавлена schema списка. Контент не зависит от User-Agent.

**Файлы:** компонент слайдера; `app/recommendations/page.tsx`, новый `client-page.tsx`; `lib/seo.ts`, `components/seo-json-ld.tsx`.

**Проверка:** без JS на главной локально есть 5 href на карточки, на рекомендациях — 20 тайтлов/40 ссылок. Production до изменений: 0/0 ссылок соответственно.

### 6. Поиск создавал индексируемые оболочки комбинаций фильтров

**Где:** `app/search/page.tsx`, унаследованные метаданные layout.

**Исправлено:** серверный `app/search/layout.tsx` задаёт собственные Title/description и noindex, follow. Поиск остаётся рабочим; внутренние ссылки могут обходиться. Canonical всех запросов на главную не устанавливается. Решение основано на назначении динамического поиска и пустом исходном HTML, а не на низком трафике.

**Проверка:** в ответе `/search?q=test` есть `noindex, follow`. Будущие ценные темы следует делать отдельными содержательными страницами после отбора, а не массово открывать комбинации фильтров.

## 🟡 Средний приоритет

### 7. Sitemap не содержал жанры и выдавал время обновления кэша как lastmod

**Где:** `app/sitemap.ts`, `sitemapAnime` и `saveAnime` в `lib/server/library.ts`. `saveAnime` устанавливает updated_at при сохранении, включая обновление кэша без изменения текста страницы.

**Исправлено:** добавлены непустые жанры из имеющихся индексированных данных с существующей классификацией тем; URL жанров кодируются и дедуплицируются. В выборке карточек отсекаются неположительные ID, расхождение ID в JSON и отсутствие названия. Удалён lastmod: достоверной отдельной даты изменения содержимого сейчас нет. Учитывается общий бюджет 50 000 URL вместе с жанрами и статическими страницами.

**Проверка:** настоящий XML-сериализатор Next используется в тестах. Локальная выборка даёт 91 URL: 50 карточек, 37 жанров, 4 статические страницы. Lastmod отсутствует. Полная проверка существования всех production URL этим аудитом не выполнялась; записи кэша не равнозначны актуальной доступности каждого источника.

**Остаётся:** свыше 50 000 URL текущая схема требует sitemap index и шардирования; сейчас production содержит 8 784 URL, поэтому предел не достигнут. Необходимо отдельно учитывать глобально удалённые карточки/запреты; географические ограничения нельзя безопасно решить одним общим sitemap. При сбое БД сохраняется прежний fallback из статических страниц, что требует мониторинга числа URL.

### 8. Связи сезонов были только клиентскими

**Где:** `components/season-navigation.tsx`, `components/anime-page.tsx`.

**Исправлено:** сервер передаёт имеющийся граф `animeRelations` в существующий компонент навигации. Его ссылки могут присутствовать уже в HTML; клиентское обновление сохранено. Запрос не инициирует внешнюю загрузку графа. Если связей в базе нет, они не выдумываются. Ошибка необязательного блока не ломает карточку.

**Файлы:** два компонента и `app/anime/[id]/page.tsx`.

**Проверка:** открыть исходник карточки с сохранённой франшизой и проверить ссылки на другие части. В изолированной выборке граф не импортировался: полнота реальных связей требует проверки рабочей базы. Нумерация и подписи остались в существующем алгоритме проекта; требуется редакционный контроль неоднозначных франшиз.

### 9. Метаданные и schema карточек требовали уточнения

**Исправлено:** Title использует существующий год без повторения, длинным названиям не добавляется длинный SEO-суффикс; при отсутствии русского имени H1 использует альтернативное. В карточке показан известный тип. Добавлен BreadcrumbList; Movie больше не получает numberOfEpisodes; неполная дата вроде одного года не выдаётся за полноценный datePublished. Новых рейтингов, отзывов и сюжетов не создавалось.

**Файлы:** `lib/seo.ts`, `app/anime/[id]/page.tsx`, `components/anime-page.tsx`.

**Проверка:** JSON.parse блоков JSON-LD; отдельно проверены Movie и TVSeries, отсутствие фиктивной даты и экранирование закрывающего script. Проверка синтаксиса и типов не заменяет внешнюю валидацию всех вариантов schema и не обещает расширенный сниппет.

### 10. Неполнота контента остаётся

Подтверждён пример `/anime/1`: описание отсутствует; метаописание корректно собирается из реальных фактов, но не заменяет сюжет для посетителя. Масштаб проблемы без инвентаризации БД неизвестен. Удаление карточек или noindex по признаку малого трафика не применялись.

Нужны отчёты только на чтение по: пустому названию/описанию; незаполненным жанрам; некорректным годам; доступности источников; дублям идентичности; пустым жанрам. После проверки источника — восстановление существующих описаний либо редакционное написание. Массовое копирование с чужих сайтов не выполнялось.

## 🟢 Дополнительные улучшения и производительность

В слайдере оставлен один H1 вместо пяти, остальные названия — H2; CSS-селекторы перенесены на класс hero-title, чтобы сохранить оформление. Файлы: `components/popular-hero.tsx`, `app/globals.css`, `app/mobile.css`. Главный постер карточки получает fetchPriority=high и async decoding; lazy loading к нему не добавлялся. LCP-фон первого слайда уже имел eager/high и не требовал повторного исправления.

Устранён немедленный повторный запрос каталога после гидратации. Карточка при наличии данных берётся из локального кэша. Публичный HTML не переведён на общее CDN-кеширование: есть географические ограничения и пользовательские функции. Сохранены private/no-store, установленные proxy для карточек.

Уже существовали оптимизация изображений в WebP/AVIF, ограничения ширины, недельное кеширование image gateway, отложенный импорт hls.js. Поэтому утверждать, что они отсутствовали, нельзя. Шрифты из внешнего Google Fonts в обследованных файлах не обнаружены.

Одиночные production-измерения TTFB до изменений: главная ~757 мс, каталог ~280 мс, page=2 ~314 мс, аниме 21 ~274 мс, аниме 1 ~260 мс, sitemap ~709 мс. Это одна точка сети без статистической значимости. Замеры Next dev включают компиляцию и для сравнения скорости production непригодны. LCP/CLS/INP и реальный выигрыш не измерены полевыми данными; численные улучшения этих метрик не заявляются. Размер и доля неиспользованного JS требуют отдельного production-профилирования; код аналитики, сезонные эффекты и общие провайдеры остаются в корневом layout.

- TypeScript и линтер затронутых SEO-модулей прошли; `git diff --check` без ошибок. Новые тесты и HTTP-скрипт: `tests/seo.test.mjs`, обновлённый `tests/sitemap.test.mjs`, `scripts/seo-http-audit.mjs`.
- Анонимный HTML проверен без сессии. В браузере подтверждена работоспособность переходов по обычным ссылкам. Гидратация и клиентская сортировка в изолированной копии не прошли проверку, как описано выше; платёжный поток, авторизация, реальные комментарии и просмотр не тестировались сквозным сценарием.
- Нет доступа к данным Вебмастера/Метрики и серверным логам ЯндексБота. Причина малого числа запросов в топ-30 не устанавливается только по технической выборке.
- Тематические подборки, `/themes`, `/browse/[source]`, `/anime/[id]/franchise`, публичные профили и остальные публичные маршруты требуют отдельной инвентаризации метаданных и ценности. Полный SEO-аудит каждого URL не заявляется.
- Номер сезона как отдельное достоверное поле в типе Anime отсутствует. Названия и связи сохранены, номера по догадке не добавлялись. Отдельный алгоритм похожих тайтлов в карточке не внедрён; рекомендации и существующие отношения сохранены.
- Когда локальный кэш ещё не содержит весь каталог внешнего провайдера, SSR показывает только сохранённые данные. Для обычного production-режима с каталогом Kodik это штатный источник; полноту импорта необходимо контролировать. Для режима только AniLiberty требуется отдельно проверить наполненность и обновление локального каталога перед выпуском.

## Данные владельца и следующий этап

Из Яндекс Вебмастера нужны выгрузки: «Страницы в поиске» и исключённые URL с причинами, «Статистика обхода» по HTTP-статусам, диагностика и безопасность/нарушения, выбранные canonical и дубли, состояние sitemap, история запросов/страниц с показами, кликами и позициями за 90 дней. Нужны примеры URL с позициями 11–30 и 31–50, настройки региона/главного зеркала, результаты инструмента рендеринга JS для нескольких карточек и жанров. Из Метрики — устройства, источники, посадочные страницы и измерения скорости. Из серверных логов — проверенные обращения ЯндексБота, ответы и задержки.

1. До деплоя владельцу проверить diff и приёмку с полным каталогом: обычный/мобильный просмотр, авторизация, коллекция, комментарии, возрастные/географические ограничения. Развёртывание — только по отдельной команде.
2. После разрешённого выпуска повторить HTTP-скрипт на production, проверить URL постера и новые жанры в Вебмастере, отправить обновлённый sitemap и небольшую выборку важных страниц на переобход.
3. Восстановить описания приоритетных существующих карточек и заполненность графа сезонов. Начать с URL с показами и позициями близко к топ-30, без выдуманных фактов.
4. Проверить полноту синхронизации и исключение глобально недоступных записей; добавить мониторинг количества URL sitemap, 5xx и пустых списков. До роста свыше 50 000 URL реализовать индекс sitemap с частями.
5. Инвентаризировать публичные дополнительные маршруты и дубли; отобрать ограниченный набор содержательных тематических посадочных страниц. Не создавать тысячи комбинаций фильтров.
6. Собрать production-профиль LCP/CLS/INP на мобильных устройствах, размеры JS и реальные задержки SQL; оптимизировать подтверждённые узкие места, отдельно оценив глобальные эффекты и провайдеры.
7. Сравнивать видимость и охват индексирования через несколько циклов обхода с исходной выгрузкой. Обнаружение страниц, серверный контент и релевантные метаданные могут помочь расширить число запросов в топ-30; позиции и сроки не гарантируются.

Официальные основания: [индексирование JS и HTML href](https://www.yandex.ru/support/webmaster/ru/robot-workings/ajax-indexing), [canonical](https://www.yandex.ru/support/webmaster/ru/robot-workings/canonical), [Sitemap и необязательный lastmod](https://yandex.ru/support/webmaster/ru/controlling-robot/sitemap?lang=ru), [robots и noindex](https://yandex.ru/support/webmaster/ru/controlling-robot/robots-txt), [статистика обхода](https://www.yandex.ru/support/webmaster/ru/service/site-indexing). SSR выбран для доступности контента; утверждение «Яндекс вообще не выполняет JS» неверно.
