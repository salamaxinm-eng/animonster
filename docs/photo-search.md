# Поиск аниме по скриншоту

## Использование и данные

Камера рядом с поиском открывает адаптивное окно. Она доступна гостям в обычной шапке, мобильной шапке и на странице `/search`.

Пользователь загружает JPG/PNG/WebP до 12 МБ, перетаскивает файл или вставляет изображение. Кнопка чтения буфера появляется только при наличии Clipboard API; отказ в доступе не блокирует загрузку. Обрезка поддерживает 16:9 и 4:3, перемещение рамки мышью/пальцем и доступные с клавиатуры ползунки. Изображения более 40 Мп отклоняются. Предпросмотр уменьшается до 1920 px по длинной стороне, отправляемый JPEG — до 1280 px и 2 МБ. Canvas удаляет метаданные исходного файла.

Файл отправляется **из браузера непосредственно** в `https://api.trace.moe/search?anilistInfo`, через multipart `image`. CORS проверен с Origin `https://animonster.su`. Ключи не используются. Нет серверного proxy для изображений и нет загрузки пользовательских фотографий в хранилище AniMonster. Перед кнопкой поиска показано уведомление о передаче кадра trace.moe. Сжатие/обрезка происходят локально. Закрытие окна, удаление и замена файла прерывают текущую операцию; ответы старых операций игнорируются.

По умолчанию включён умный поиск: до четырёх последовательно проверяемых вариантов кадра, без параллельных запросов и повторов при ограничении сервиса. При сходстве от 94% дальнейшие варианты не отправляются. Идентичные JPEG не отправляются повторно. Сходство ниже 90% не показывается как распознанный тайтл. Ручные режимы «Весь скриншот», 16:9 и 4:3 сохраняются; в ручном режиме зеркальный поиск доступен отдельной кнопкой, если совпадений нет. До трёх уникальных AniList ID сортируются по максимальному сходству среди вариантов; повторное появление ID не повышает оценку искусственно. Сходство не называется вероятностью. `episode` принимается как число, строка или отсутствующее значение, время сцены показывается только при корректных значениях. Превью допускаются только по HTTPS с `api.trace.moe` и `media.trace.moe`.

Обрабатываются квота/402, 429, Retry-After при его доступности браузеру, 5xx, сетевые ошибки, некорректные ответы и таймаут 12 секунд на вариант и 65 секунд на весь пользовательский сценарий, включая проверку каталога. При сбое позднего варианта сохраняются ранее найденные допустимые совпадения с предупреждением. Лимиты trace.moe не зашиты в код.

## Сопоставление с AniMonster

`POST /api/photo-search/resolve` принимает только 1–3 положительных числовых AniList ID. Изображения и произвольные URL не принимаются. JSON ограничен 1 КБ при чтении потока. Используются существующая проверка Origin и отдельный префикс счётчиков в `auth_limits`: до 30 запросов проверки каталога за минуту на IP. Регистрация не требуется.

Порядок сопоставления:

1. Уже имеющийся `anilist_id` в JSON `anime_cache`, если такая связь присутствует. Сейчас отдельной таблицы AniList-связей в проекте нет.
2. Сервер получает доверенные данные по этому ID из AniList GraphQL. MAL ID сопоставляется с **явным** `mal_id` нашего каталога. Равенство Shikimori ID и MAL ID не предполагается.
3. При отсутствии ID-связи требуется точное совпадение одного из основных названий AniList с названием/альтернативным названием каталога, совпадающий год и совместимый формат (TV, фильм, OVA, ONA, special, music). Общие синонимы франшизы AniList не используются для выдачи ссылки. Нечёткий поиск не выбирает сезон автоматически.
4. При нескольких кандидатах ссылка не выдаётся. Неоднозначность и недоступность проверки отличаются от сообщения «Пока нет в каталоге».

Данные AniList хранятся семь дней в существующем `catalog_page_cache`; при временном сбое доступны последние сохранённые сведения. Повторные одновременные запросы одного ID объединяются. На 429/5xx действует временная пауза запросов к AniList. В кэш не записываются заголовки, присланные браузером, или фотографии. Данные каталога не изменяются, новые аниме не создаются. Дополнительная таблица соответствий и миграция не требуются.

Кнопка ведёт на `/anime/[id]`. Параметры серии/плеера не добавляются: достоверного соответствия нумерации trace.moe и провайдеров плеера в проекте пока нет.

## Ограничения

trace.moe ищет визуально похожие сцены в своей базе. Кадры с монтажом, надписями, сильным кропом или фильтрами могут не распознаться. В базе есть не все аниме. Предпросмотры временные (по документации около пяти минут); ошибка картинки скрывает её, не ломая результат. Доступность и квота зависят от сервиса и IP пользователя. AniList используется для названий и проверки каталога; при его недоступности распознанные кадры всё равно показываются. Clipboard API и разрешения различаются между браузерами.

Документация: https://soruly.github.io/trace.moe-api/

## Умная подготовка кадров — 2026-10-28

Поиск области сцены работает локально на превью до 384 px по длинной стороне. Статистика цветовых корзин по строкам/столбцам отделяет протяжённую текстурированную сцену от однотонных полей; редкие подписи/кнопки на полях не должны определять границы. Сохраняется возможность отменить автоматическую обрезку и выбрать область самостоятельно.

Первым отправляется обнаруженный кадр с сохранением всех его доступных частей. Затем проверяются вариант с локальной обработкой типичных светлых субтитров с тёмной обводкой и зеркальный вариант. Обработка ищет группы маленьких компонентов, выровненных как строка текста, расширяет маску обводки и заполняет её ближайшими немаскированными цветами; это не OCR, не нейросетевая реконструкция и не восстановление утраченных частей кадра. Оригинальный вариант остаётся кандидатом. Размер обработки ограничен 640 px, число компонентов ограничено 600, чрезмерные маски отклоняются. Четвёртый вариант для вертикального изображения — горизонтальная область внутри обнаруженной сцены; для иных нестандартных пропорций — гипотеза 16:9, иначе исходный скриншот. Геометрические гипотезы не получают бонуса сходства.

Новые тесты `tests/photo-search-smart.test.mjs` проверяют смещённый кадр на вертикальном скрине с подписями на полях, цветные/белые поля, отсутствие обрезки обычных/тёмных кадров, ограниченное изменение субтитров с сохранением оригинала, последовательность/лимит/дедупликацию запросов, раннюю остановку, отсутствие искусственного роста оценок, фильтрацию слабых совпадений, отмену и остановку на квоте с сохранением найденного.

Живой CLI-тест официального примера trace.moe (Nekopara OVA, AniList 99939) с добавленной подписью: исходный подписанный кадр 95.73%, локально обработанный 97.30%. Вертикальная композиция с полями, зеркальным кадром и подписью распознана как тот же тайтл после зеркального варианта (93.28%). Это отдельные примеры, не общая метрика точности.

Два присланных пользователем TikTok-скрина также проверены живым API с разными гипотезами; надёжного распознавания нет. Варианты давали посторонние тайтлы с низким сходством, в том числе 82.12%; такие ответы теперь скрываются. Не добавлялись подстановки названий, специальные исключения для этих картинок или искусственные оценки. Сами пользовательские изображения в Git и на сервер не копируются.

Открытая модель WD EVA02 Tagger отдельно проверена как эксперимент: на одном из скринов выдала общие теги, без имени персонажа. Не включена в продукт. На сервере нет ключа подходящего vision API; платный семантический fallback не подключён и не оплачен. Для сильно обрезанных TikTok-кадров одного trace.moe недостаточно. Любую дополнительную модель необходимо сначала проверить на пользовательских примерах, а затем согласовать провайдера/бюджет и описание передачи данных.

Текущая вёрстка живого сайта не проверялась из-за прежнего ограничения доступа. Использованы исходный код, TypeScript, линтер, модульные/интеграционные тесты и CLI Canvas/Sharp с живыми ответами trace.moe. Прежняя запись об эмуляции браузеров выше относится к первоначальному выпуску функции.
